# MSN Cricket Auction Platform
## Product Requirements Document · v1.0 · 12 November 2026

Status: proposed implementation baseline. Requirements confirmed in conversation are distinguished from recommended defaults. This document supersedes the scope implied by the early local demo; that demo is an experiment, not the production foundation.

## 1. Product intent
A bilingual, mobile-first auction service for cricket clubs in Kerala. Players register for a club's auction; team managers register or receive invitations; the club approves participation. An auctioneer conducts the event in an auditorium while approved managers bid from phones. A presentation screen shows the player, accepted bid, leading team and team squads. Other clubs purchase licenses for one auction or a package of auction credits.

The product succeeds when an organizer can prepare, rehearse, run and reconcile a complete auction without spreadsheets becoming the source of truth. Virtual points determine player allocation. Actual money is collected only for platform licenses; player bids do not create payment obligations.

## 3. Recommended defaults and boundaries
These are product decisions proposed for implementation, not additional user-confirmed requirements.

- Responsive installable web app/PWA; no app-store installation required. Online access is required to bid.
- One active bidding operator per team per auction. Other approved members can view their team's information. Operator handover is explicit and audited.
- One active lot per auction. Different clubs may run auctions simultaneously.
- Auctioneer closes bidding manually. An optional visual countdown supports the auctioneer but does not automatically sell a player in the first release.
- No skipped bid amounts: manager taps the server-provided next bid. Configurable fixed increments initially; value-based increment bands can follow once needed.
- Optional player base-rate request is reviewed by the club. Missing base rate resolves to the auction's default base points at approval. Lock the effective base before the event.
- Reserve enough points to fill the remaining minimum squad at the auction minimum base points. Club can disable this rule before locking the auction and sees an explicit warning.
- Player profile is reusable; registration, approval, base points and sale outcome belong to each auction separately.
- Licenses are credit-based, not recurring subscriptions initially. Package size, price, tax and validity are configurable. No assumed pricing or automatic renewal.
- Registration is account-based with verified email initially; phone recorded as contact. SMS OTP requires a selected provider and separate onboarding.
- Suggested initial scope is adult community cricket; junior participation and guardian consent require a defined policy before enabling under-18 registration.

## 5. User journeys
### Club onboarding and licensing
Create account → create club and branding → select single credit/package → online checkout or manual purchase request → verified payment/manual grant → credit balance → create auction draft. Draft creation does not consume credit. Starting a real auction consumes exactly one credit. Rehearsals use separate sample data and cannot publish real results.

### Auction preparation
Create auction → set rules and dates → publish registration link/QR → invite managers or accept applications → approve players and manager-to-team assignments → review missing data and duplicates → preview screen → readiness checks → lock roster and rules → begin.

### Player
Open club registration link → authenticate → select/create profile → provide details and optional requested base points → consent to profile display → submit → see pending/approved/rejected/changes requested status → edit while permitted → view assigned team/results after auction. Rejection reasons visible privately. A withdrawn registration cannot be selected.

### Manager
Open invite or apply → authenticate → club approves team assignment → view rules, approved player pool, own purse and squad → enter live room → receive connection/sync status → tap next bid → await accepted/rejected result → see winning team and purse after confirmed sale. A pending animation never implies acceptance.

### Auctioneer
Choose next eligible player manually or randomly → preview details → open bidding → observe accepted bids → pause/resume if needed → close bidding → confirm winning bid and mark sold, or mark unsold if no bids → display result → proceed. Random selection records the chosen eligible pool and outcome for audit; it is not a claim of independently verifiable randomness.

## 7. Auction rules
Points are non-negative integers, never floating point. Minimum bid on first offer equals the effective base. Further bids equal the current accepted amount plus configured increment. Current leader cannot bid again. Maximum squad blocks any further purchase. If reserve protection is enabled, affordability is:

`maxBid = remainingPurse - max(0, minimumSquad - currentSquadSize - 1) × minimumBasePoints`

The rule protects only a minimum-points floor; it cannot guarantee enough suitable players will remain. An auction where `purse < minimumSquad × minimumBasePoints` fails setup validation. Per-player base cannot be below the auction minimum. Published rules explicitly state that server acceptance order determines the winner of simultaneous requests; client tap time and hall observation do not override it.

Late bid versus close is resolved by the same database lock: whichever valid command commits first determines state. Once close wins, no new bids enter that lot. A visual countdown has no independent authority.

## 9. Reliability and performance targets
Proposed initial validation envelope: 10 concurrent auctions, each up to 20 teams, 300 players and 500 read-only viewers; 50 competing bid requests/second per auction in stress tests. These are test targets, not a capacity claim.

Bid acceptance response p95 ≤500ms and committed update to connected display p95 ≤1 second under the test envelope, measured in an India-region deployment with documented network conditions. Reconnection and full snapshot p95 ≤5 seconds after connectivity returns. No accepted bid lost after acknowledgment; backup disaster recovery targets RPO ≤5 minutes and RTO ≤60 minutes, subject to purchased hosting/backup plan. Event-day manual rehearsal and recovery drill are required.

## 10. Scope exclusions and launch decisions
No match scoring, fixtures, fantasy wagering, player payments, automated AI valuations, native apps or offline bidding in the initial product. A full LAN-only deployment is a separate operating mode requiring packaging, local networking and reconciliation design.

Before public launch: confirm product name, club branding, license pricing/package expiry/refund policy, merchant ownership/payment provider, hosting budget, retention duration, minor eligibility and support contact. These do not block design or implementation using adapters and proposed defaults. Do not fabricate credentials or live payment success.

## 11. Definition of release readiness
Complete one rehearsal from club onboarding through purchase/manual credit, player/manager approvals, locked setup, multi-device bidding, intentional disconnect, simultaneous bid, sold/unsold recall, correction and reconciled exports. Pass tenant/role security tests, restore a backup, validate English/Malayalam screens, and demonstrate operation on real phones plus projection. Production launch requires configured merchant/hosting identities and club acceptance of published rules.

# MSN Cricket Auction Platform
## Detailed Solution Architecture · v1.1 · 12 November 2026

Read with MSN_Cricket_PRD.md. Technology stack approved by the product owner. Remaining proposed defaults are identified in the PRD. This describes the intended implementation, not the current demo.

## 1. Architecture decision
Use a modular TypeScript application with a Next.js/React web interface with Tailwind CSS and accessible components, a long-running NestJS API/realtime service on Node.js, PostgreSQL as the authoritative store, object storage for photos/logos and a background worker for reliable event delivery and notifications. Deploy in an India region where the selected providers support the required services. Keep frontend and backend contracts explicit. No microservice fleet or Kubernetes is needed for the first release.

| Approach | Benefit | Tradeoff | Decision |
|---|---|---|---|
| Browser-only state | Fast design experiments | Cannot enforce shared bids, persistence or identity | Existing demo only |
| Managed database + thin serverless CRUD | Low operational effort | Auction commands, realtime delivery and recovery still need a consistent authority | Viable alternative with custom command service |
| Modular backend + PostgreSQL + persistent realtime | Clear transaction boundary, replay and operational control | Requires managed runtime and monitoring | Recommended |

Approved stack: TypeScript across web and backend; Next.js + React for web, Tailwind CSS for styling, NestJS for the persistent API and Socket.IO gateways, PostgreSQL for authoritative data, and S3-compatible object storage. Use managed containers for the persistent backend and managed PostgreSQL. Redis is optional when multiple backend replicas need fanout; it is not an initial correctness dependency.

Pin supported dependency versions when implementation begins. Hosting provider and authentication provider remain replaceable adapters. Do not couple the auction engine to payment or messaging vendors.

## 5. Auction command transaction
For `placeBid`, receive authenticated actor, auction/lot ID, `commandId`, expected lot version and expected amount.

1. Validate schema/size and authenticate. Rate-limit by user and auction, independently of authorization.
2. Begin PostgreSQL transaction. Lock auction row, then active lot, then team row using the same order for all mutations.
3. Resolve club/auction membership and active operator assignment within the transaction. Check approved team, licensed started auction, open lot and unchanged version.
4. Check idempotency record. Same actor/command ID and request hash returns stored outcome; changed payload with reused ID is rejected.
5. Calculate next valid amount and maximum affordable bid from authoritative rules, allocations and purse. Reject own-team leading bid and ineligible/full squad.
6. Insert accepted bid, advance lot and auction sequence/version, write event, audit and outbox record, and record command outcome.
7. Commit. Only then acknowledge acceptance and broadcast the committed event. Timeout after commit is resolved by command-status lookup, not by a second bid with a new ID.

Serialize close, sell, recall and corrections through the same auction lock. At the initial scale this intentionally trades per-auction write parallelism for simple correctness. Different auctions use different locks. Set transaction/lock timeouts; safely retry deadlock/serialization failures with the same command ID. Never use SKIP LOCKED for auction bidding because silently skipping the active authority row would violate ordering.

PostgreSQL's row locks support this proposed serialization boundary; see https://www.postgresql.org/docs/current/explicit-locking.html .

## 6. State machines
Auction: DRAFT → REGISTRATION_OPEN → READY → LOCKED → LIVE ↔ PAUSED → COMPLETED → ARCHIVED. Explicit cancellation permitted before LIVE; in-progress abandonment is an audited administrative workflow. Roster/rule unlocking before start returns to readiness review; after start requires controlled amendment and a new rules version.

Lot: PREVIEW → OPEN ↔ PAUSED → CLOSED → SOLD or UNSOLD. CLOSED preserves the leading bid for confirmation. An operator can reopen a closed but unsettled lot only with a reason and a new version; this is visible to all clients. SOLD reversal creates compensating records, never deletes bids. A recalled UNSOLD registration gets a new lot attempt.

Registration: DRAFT → PENDING → APPROVED / REJECTED / CHANGES_REQUESTED; withdrawal allowed before lot opening. Manager application follows equivalent approval transitions. A platform suspension during an active event pauses new commands rather than erasing entitlements or results.

## 7. Realtime protocol and client correctness
Socket.IO is selected for delivery through NestJS gateways; room subscription requires authorization to the requested club/auction. Public projection uses a separate redacted stream. Event envelope includes `eventId`, `auctionId`, `sequence`, `lotVersion`, `type`, `occurredAt`, `payload`.

On connect: authenticate → authorized subscription → fetch snapshot with cursor → replay events after cursor → apply only contiguous sequences → enter synchronized state. A missing sequence, changed lot or failed recovery triggers fresh snapshot. Duplicate event IDs are ignored. Keep an event retention window and respond `RESYNC_REQUIRED` for expired cursors.

Socket transport alone is insufficient for reliable outcomes: default Socket.IO delivery is at most once. Application commands therefore use acknowledgments/idempotency, and events use durable replay. Sources: https://socket.io/docs/v4/delivery-guarantees/ and https://socket.io/docs/v4/tutorial/handling-disconnections/ .

Use HTTPS command endpoints for mutations and sockets for notifications; never implement two independent bid processors. Show reconnecting/stale state immediately, disable bid until fresh snapshot, and never queue offline bid submissions. A foregrounded phone resynchronizes before enabling controls. Losing connection after submission displays 'Checking bid result' and queries the original command ID.

## 9. License and payment correctness
A payment return URL never grants a license. Verify signed provider webhooks against the raw request; deduplicate provider event IDs; validate merchant, amount, currency and internal order binding. Payment processing and credit issuance are one transaction. Failed/replayed notifications cannot issue duplicate credits. Reconciliation worker checks unresolved orders with provider status.

Manual grants require platform permission and recorded reason/reference. Starting an auction locks available credit grants in deterministic order, excludes expired/revoked units and inserts one redemption keyed by auction ID. Restart/resume never consumes another credit. Refunds and chargebacks revoke unused units; consumed units create a billing exception reviewed by support. An in-progress auction is paused only by explicit operator action, not an automatic destructive refund handler.

Rehearsal records are marked separately and cannot be converted to real accepted bids. Package validity and cancellation/recredit policy are configurable business terms, not hidden assumptions.

## 10. Security and privacy
Use managed identity or an established auth library; no custom password cryptography. Secure HttpOnly/SameSite cookies, CSRF protection for browser mutations, session rotation, admin MFA and tenant membership revalidation. Database row-level security is recommended as defense in depth with transaction-local tenant context and no pooled-connection context leakage; application checks remain mandatory. Realtime subscriptions enforce equivalent scopes.

Private storage with signed URLs; validate MIME by bytes, file size and image dimensions, strip EXIF, re-encode images and scan uploads. Public derivative photos need explicit publication permission. No contact, birth date or consent records in public streams, logs or CDN caches. Keep audit sensitive-field redaction. Define retention/deletion schedules before launch; allow profile deletion/anonymization while retaining non-identifying auction accounting. Legal requirements are a launch review item, not asserted compliance certification.

## 11. Deployment, reliability and operations
Separate development, staging and production identities, databases, buckets and merchant keys. Deploy web and persistent API/worker containers behind TLS. PostgreSQL uses managed backups and point-in-time recovery. Optional Redis supports connection fanout/rate limits at multiple API replicas; PostgreSQL remains authority. A failed Redis layer must not produce a second auction leader or accept uncommitted bids.

Use rolling deploy compatibility and expand/contract migrations. Avoid schema changes and deployments during a live event. Monitor accepted/rejected bids, command latency, lock waits, event publication lag, client disconnect rates, outbox backlog and reconciliation deltas. Correlate logs through command ID and event sequence. Alerts go to event operators through an agreed support channel.

Venue readiness: dedicated organizer laptop, projection connection, tested Wi-Fi for all team operators, separate audience network where possible, backup mobile connectivity and UPS for critical venue equipment. Internet failure pauses bidding; previously committed results remain durable. No automatic offline merge. For major outage export latest confirmed state, record manual continuation separately and reconcile under admin review before publishing final results.

## 12. Architecture boundaries requiring verification
Load-test actual deployment against PRD envelope; benchmark Malayalam fonts on real devices; verify merchant webhooks in provider sandbox; test database restoration and pool/RLS isolation; prove stale/disconnected clients cannot change closed lots. Infrastructure pricing and provider-specific sizing require measured traffic and chosen accounts. This architecture does not claim the current local demo satisfies any of these controls.

## 4. Domain implementation contract
Represent points with validated safe integers and explicit bounds. Define AuctionRules, RegistrationStatus, AuctionStatus, LotStatus, TeamState, BidCommand and AuctionEvent in shared contracts. No UI writes to balances. Current bid is derived from the committed leading bid record.

Pure domain functions:
- resolveEffectiveBase(requestedBase, approvedOverride, rules): valid non-negative integer respecting minimum; no silent invalid fallback.
- computeMaxBid(team, rules): remaining purse minus configured minimum-squad reserve.
- validateNextBid(state, actorTeam, expectedVersion, amount): typed acceptance or rejection, without persistence side effects.
- validateTransition(state, command): enforce legal auction and lot transitions.
- computeSettlement(lot, team): allocation and ledger delta for a closed lot with a winning bid.
- validateReversal(allocation, currentState): identify downstream conflicts before compensating entries.

Persistence services perform these calculations after acquiring locks. A command succeeds only after commit. Domain tests cover boundaries; integration tests prove database locking and constraints, which pure unit tests cannot prove.

## 5. Critical transaction recipes
### Start auction and redeem license
Lock auction → verify LOCKED/readiness → if already started return original outcome → lock eligible grants → calculate unused units excluding existing redemptions → insert unique redemption → set LIVE → append event/outbox/audit → commit. Concurrent starts return the same result or a conflict, never consume twice.

### Sell player
Lock auction → lot → winning team → registration/allocation scope → verify CLOSED and leading bid → recompute eligible balance/squad → insert allocation → decrement purse and append ledger → mark SOLD → event/outbox/audit → commit. Failure rolls back all changes. Settlement command retry returns original result.

### Correct result
Pause auction → identify sale and dependent actions → validate whether reversal would violate state → preview resulting purse/squads → admin confirms reason → compensate ledger and allocation → mark prior outcome reversed → create explicit recall attempt if requested → publish correction → reconcile → resume. Block arbitrary historical editing if subsequent purchases depend on it; require a documented resolution instead.

### Crash after commit, before broadcast
Worker finds pending outbox → publishes event → marks delivered. If worker crashes after publishing, event can repeat; clients deduplicate by event ID/sequence. On reconnect clients fetch authoritative snapshot regardless of local optimistic state. Never promise exactly-once network delivery; guarantee one logical database effect through idempotency and constraints.

## 6. UX specification by screen
### Auction creation
Save draft at each step. Present rules as a readable summary with units in points. Readiness list links to unresolved issues. Lock action shows a final rule snapshot and affected approved teams/players. Changes before start invalidate readiness and require relocking.

### Registration and approval
Separate player profile from auction entry. Required: name, photo, age/date-of-birth input per policy, contact, location, role, batting style, bowling style or not applicable. Optional requested base points clearly labelled. Approval queue filters by role and status, shows missing fields, supports request changes and individual review. Bulk approval requires selection review; duplicate email/phone is a review signal rather than silently deleting entries.

### Manager phone room
Top: auction name, live/paused and connection state. Main: player photo/name, role, styles and base; accepted bid and leading team. Sticky bottom: next bid amount, own purse, maximum eligible bid and primary action. Disable when leader, full, unaffordable, paused, pending or stale; explain why. Tabs: player pool, watchlist if included, own squad and all teams. Watchlists are optional convenience, not launch-critical.

### Auctioneer console
Left: eligible queue and role/status filters. Centre: preview/current player and bid feed with server timestamps. Right: team purses/slots and connection indicators. Primary actions vary by state: open → close → confirm sold. Unsold only when no accepted bid. Pausing is always prominent. No global keyboard shortcut can sell without deliberate confirmation.

### Projection
Use redacted endpoint/stream only. Display token is read-only, scoped to one auction, revocable and rotated after event. Full-screen mode is user-triggered. Do not expose contacts even in HTML source or network payload. Include stale connection indicator; do not continue animations that imply new bids after disconnect. Between lots show team squad and purse summaries. Public URL access respects club visibility settings.

### Platform billing console
Show order state, verified payment reference, credits granted/used/remaining and manual grant history. A manual grant requires count, club, reason and optional external payment reference. A user-entered payment reference does not mean verified online payment.

## 8. CI and quality gates
Every change: format, lint, typecheck, domain tests, database integration tests and production build. API/security changes include negative tenant/role tests. Live engine changes include concurrency and replay tests. UI changes receive responsive visual inspection and automated accessibility checks, then real keyboard/phone testing for critical flows. Record failures honestly; no 'ready' status while acceptance tests are skipped.

Use seed data with fictional Kerala club/team/player identities and visibly mark sample environments. Never copy real player contact details into test fixtures. Keep secrets out of source and logs. Preview environments use sandbox merchant keys and isolated databases.
